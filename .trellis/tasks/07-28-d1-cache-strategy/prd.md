# D1 缓存策略设计

## Goal

在完整核对本地 D1 表结构、索引、查询、写入与公开页面数据流后，设计一套以 D1 为唯一事实来源、显著减少免费额度消耗且不降低页面正确性、可用性或交互流畅度的缓存方案。

## Background

- 项目运行在 Astro SSR + Cloudflare Workers 上，动态活动数据通过 Wrangler 的 `DB` 绑定访问 D1。
- 当前公开首页、热门榜、活动列表、详情、标签搜索与 sitemap 均存在请求时 D1 读取；详情页另有独立访问统计写入。
- 当前已有的热门榜 `Map` 缓存只存在于单个浏览器页面会话，不能减少跨用户或刷新后的 D1 访问。
- 用户明确要求先实际检查本地数据储存设计，再制定不会影响用户体验的缓存方案。
- 全新临时 D1 中的开发数据为 143 个活动、10 个规范标签、24 条活动标签关系和 91 条匿名访客记录；已发布活动覆盖 14 个精确地区代码。
- 地区目录来自应用内 `cn-division`，共 3310 个有效省/市/区县选项，不存在 D1 `cities` 表。
- 标签联想在两个客户端组件中均以 160ms debounce 请求 `/api/tags`，是高频小查询入口。
- 当前查询计划证明热门窗口、访客清理和 sitemap 可以在不改变业务语义的前提下更充分使用现有索引。
- 当前详情页每次由浏览器执行 JavaScript 后都会额外 POST `/api/events/:id/view`；该 POST 每次运行一个包含“清理过期访客 + 当日 upsert”的 D1 batch。
- 本地临时 D1 验证表明，同一活动、同一访客在同一中国本地日期的第二次 upsert 逻辑变更行数为 0，但仍会产生一次 Worker 请求和 D1 操作；首次记录的逻辑变更行数为 1。
- `event_visitors` 同时具有复合主键和 `last_seen_date` 二级索引。Cloudflare 按表和受影响索引分别计算写入行，因此不能把 10 万 D1 写入行简单等同于 10 万独立访客。
- `getDB()` 当前在每次取得绑定时执行 `PRAGMA foreign_keys = ON`；D1 官方文档确认外键默认始终启用且用户查询无法关闭，因此这是所有动态请求上的无效数据库往返。
- `src/lib/db/queries.ts` 当前为 1008 行，混合公开读取、热门统计、标签、投稿、管理员写入和审计；`getPublicEvent()` 还会先读取完整 `events.*`，再在 JavaScript 中过滤公开状态。
- 管理员编辑活动当前先读状态，再按标签串行查询或插入，随后无条件删除并重建全部标签关系，最后单独写审计；标签越多，D1 调用数越高，未变化的关系也会被重复写入。
- 服务部署在 Cloudflare 免费方案。当前 `wrangler.jsonc` 未配置 `routes` 或自定义域，默认落在 `*.workers.dev`；官方文档只保证自定义域和 Pages 域具备可用的 Cache API 操作。目标自定义域名为 `acg.hobr.site`。
- 免费方案的四条额度按最先撞线排序为：CPU 10 ms/请求、Worker 100,000 请求/日、D1 5,000,000 `rows_read`/日、D1 100,000 `rows_written`/日。Cache API 调用与 D1 调用共用每次调用 50 个 subrequest 的配额。

## Requirements

- R1. 方案必须以当前迁移、索引、查询函数、公开路由、客户端请求和管理员写入路径为证据，不得仅套用通用缓存模板。
- R2. D1 必须保持活动、标签、审核状态和访问热度数据的唯一持久化事实来源；缓存不得演变成第二套可独立修改的数据源。
- R3. 公开用户不得看到跨地区、跨筛选条件、跨活动或跨状态串用的数据。
- R4. 缓存命中、缓存未命中、缓存写入失败和 D1 暂时失败时，页面导航、错误提示和已有降级行为必须保持可用。
- R5. 管理员创建、编辑、审核、下线、重新发布、标签归并和批量导入后，公开数据必须在明确且可验证的失效边界内更新。
- R6. 投稿、管理员接口、访问统计 POST、鉴权响应和任何用户相关响应不得进入共享公共缓存。
- R7. 方案必须分别定义缓存对象、规范化缓存键、TTL、失效机制、并发回源控制、错误降级、监控指标和回滚方式。
- R8. 方案应优先保护 Workers Free、D1 Free 和 KV Free 的共同额度，不得为了节省 D1 而无约束地把压力转移到更紧的 KV 或 Worker 请求额度。
- R9. 方案必须覆盖首页 SSR 与无刷新地区/热门切换、活动列表及筛选、活动详情、标签搜索、sitemap 和访问统计链路。
- R10. 缓存设计不得改变现有公开响应字段、页面呈现、排序、分页、地区解析、热度口径、审核状态机或隐私约束；允许新增仅供服务器内部使用的逐字段公开投影类型。
- R11. 管理员成功修改公开数据后，正常服务期间任何公开页面/API 最多允许 60 秒陈旧；超过 60 秒必须阻塞回源，不得继续以后台刷新名义返回旧数据。
- R12. D1 暂时失败时可以短时返回已验证的安全陈旧 DTO，但必须设置明确上限和可观测标记；D1 恢复后不得继续优先返回故障陈旧数据。
- R13. 缓存未命中的 D1 查询必须同步完成已验证的无语义索引优化，不新增没有当前数据规模证据支持的索引。
- R14. 热度必须继续表示近 3/7/30 日内按活动隔离的独立 IP 访问；不得改成 PV、每日独立访客相加、近似计数或浏览器身份计数。
- R15. 同一活动、同一事件级访客键、同一中国本地日期的重复访问，在已有一次 D1 成功记录后应优先绕过 D1；任何缓存丢失、跨数据中心或并发竞争只能造成额外 D1 校验，不得造成少计或重复访客行。
- R16. 访问标记只能在 D1 已确认存在当日访客记录后写入。D1 失败、无效活动、已结束活动或缓存写入失败时不得留下会阻止后续合法记录的假阳性标记。
- R17. 访客过期清理不得继续位于每次详情访问的关键路径；必须改为索引化的低频维护任务，维护延迟不得改变热门榜结果。
- R18. 热门榜读取允许按已批准的 25-35 秒新鲜期和 60 秒正常上限更新，不得因每个新访客主动清空所有热门缓存而制造回源风暴。
- R19. 数据库访问层必须做针对性职责收口，移除每请求无效数据库操作，并让公开读取、热度、标签和管理员业务写入具有清晰边界；不得引入 ORM 或泛化 Repository 框架。
- R20. 所有公开活动查询必须在 SQL 中完成公开状态过滤并使用显式公开字段投影；不得先读取完整 `EventRecord` 后再删除或忽略私有字段。
- R21. 管理员创建、编辑、状态变更和标签归并必须通过业务操作函数完成。操作函数应返回结果状态及缓存失效所需的活动 ID、旧/新地区和旧/新状态，路由不得为构造失效信息再次查询 D1。
- R22. 标签解析必须使用基于 `json_each()` 的集合式插入和关系维护，消除随标签数量增长的串行 SELECT/INSERT；编辑时只新增和删除关系差异，不得无条件全删全写。
- R23. 相关写入和审计应在 D1 `batch()` 能安全保持现有结果语义时放入同一原子批次；冲突、幂等成功、404/409 状态码和已有审核状态机不得因减少调用而改变。
- R24. 已经按职责并行或 batch 的独立公开读取不得为了追求单次调用而强行合并成巨型 SQL；数据库调用数、`rows_read`、`rows_written` 和页面延迟必须分别衡量。
- R25. Cache API 相关能力必须以 Worker 绑定自定义域名为前提。官方文档只保证自定义域（及 Pages 的 `*.pages.dev`）具备可用的 cache 操作，`*.workers.dev` 不在该列表内。域名绑定完成并在真实 hostname 上通过 `put` / `match` 探针前，不得启用任何公开数据缓存 scope。
- R26. 方案必须显式管理 Workers Free 的 10 ms CPU/请求预算。实施前后需分别记录按路由的 CPU time 基线；缓存命中省下的是 D1 等待而非 CPU，任何新增序列化、摘要计算和 `waitUntil` 后台工作都必须计入该预算并可回滚。
- R27. 单次调用的 D1 调用与 Cache API `put`/`match`/`delete` 共用 Workers Free 的 50 subrequest 配额，方案必须为读取路径和写后失效分别设定显式上限，不得出现随数据规模增长的无界扇出。
- R28. 写后失效必须覆盖受影响地区码的祖先前缀（省/市/县），因为公开查询对 2 位和 4 位地区码使用前缀匹配；只失效精确地区码不满足"本地立即失效"的承诺。
- R29. `tags,sitemap` pilot 稳定后，公开 DTO 缓存应由外部控制面自动逐 scope 晋级，不再要求站点负责人逐次手动确认；Worker 运行时不得持有可修改自身版本或变量的 Cloudflare 写权限。
- R30. 自动晋级顺序固定为 `popularity -> homepage -> detail -> list`，每次只增加一个 scope；访问去重使用独立开关和独立门禁，不属于本自动序列。
- R31. 每次晋级必须以当前已提交源码、远程 D1 schema 兼容、候选路由响应与 D1 投影一致、CPU p99 < 10 ms、`exceededCpu = 0` 且错误率未恶化为前提。任一指标缺失、超时或结果不明确都必须 fail closed，不得晋级。
- R32. 自动发布必须保留上一稳定 Worker Version，候选失败时恢复上一版本 100% 流量并冻结后续晋级；回滚不得删除、重建或修改 D1 事实数据。
- R33. 所有新 scope 必须先完成路由接入、DTO guard、规范键、TTL、错误降级和测试，再进入自动发布。自动控制器不得通过只修改 `PUBLIC_DATA_CACHE_SCOPES` 启用尚未接入的空实现。

## Acceptance Criteria

- [ ] A1. 研究材料列出所有 D1 表、索引，以及公开读取和业务写入路径，并标明每条链路的当前查询/写入形态。
- [ ] A2. 设计为每类公开数据给出安全缓存键和 TTL，并证明地区、窗口、过滤条件、分页、活动 ID 和内容版本不会串用。
- [ ] A3. 首页基于 IP/查询参数的地区选择不会因共享缓存而向用户展示错误地区内容。
- [ ] A4. 管理员成功写入后，受影响的公开缓存可以立即或在已批准的最短时间内失效；失败的失效操作不会回滚已提交的 D1 事务，也不会永久保留旧数据。
- [ ] A5. 缓存不可用时自动回源 D1；缓存写入失败不会让原本成功的页面/API 请求失败。
- [ ] A6. D1 暂时失败时，方案明确哪些已有缓存可安全作为陈旧数据返回、可陈旧多久，以及用户能看到的提示或响应头。
- [ ] A7. 设计明确比较 Cache API、Workers Cache、KV 和仅浏览器缓存的额度、命中范围与复杂度，并选择与当前 Astro Worker 结构相符的最小方案。
- [ ] A8. 访问统计的读取与写入优化单独处理；缓存公开详情页不会错误地阻止合法的独立访客统计。
- [ ] A9. 实施计划包含本地 D1、路由、并发、失效、错误注入、类型检查、测试、lint 和生产构建验证。
- [ ] A10. 方案含分阶段发布、命中率/D1 行读取监控、快速关闭缓存的回滚开关，不要求一次性大改。
- [ ] A11. 自动化测试证明缓存年龄不超过 60 秒时可无闪烁后台刷新，超过 60 秒时正常服务必须阻塞取得新值。
- [ ] A12. `EXPLAIN QUERY PLAN` 证明热门窗口、访客清理和 sitemap 使用现有目标索引，且结果集、排序和中国本地时间口径保持不变。
- [ ] A13. 热度写入测试证明首次或跨日访问会更新 `event_visitors`，同日重复访问不会产生逻辑行变更，3/7/30 日查询结果与当前语义一致。
- [ ] A14. Cache API 访客标记按活动级访客摘要和中国本地日期隔离；仅在 D1 确认后写入，命中时绕过 D1，丢失或跨数据中心时由 D1 主键和条件更新保持正确。
- [ ] A15. 已确认记录的重复详情访问可在 SSR 阶段省略独立统计 POST；标记不可用、IP 变化、活动变化或跨日时仍发送现有后台 POST，页面正文和交互不等待统计完成。
- [ ] A16. 过期访客由每天一次的 Worker Cron 使用 `idx_event_visitors_recent` 清理；Cron 延迟或单次失败只影响存储回收，不影响热门查询正确性或页面请求。
- [ ] A17. 监控分别展示 Worker 请求、热度标记命中/未命中、D1 `rows_read` / `rows_written` 和统计错误，且日志不包含原始 IP、访客键或标记摘要。
- [ ] A18. `getDB()` 只校验并返回绑定，不执行 D1 statement；迁移中的外键声明和 D1 默认外键约束仍正常生效。
- [ ] A19. 自动化测试证明公开首页、热门、列表和详情 DTO 均来自显式公开投影，且不包含 `submitter_contact`、`tag_suggestions`、`reject_reason` 或其他管理字段。
- [ ] A20. 审核通过、驳回、下线和重新发布保留现有 changed/already-target/conflict 语义；正常 changed 路径最多两次 D1 binding 调用，冲突或幂等路径最多一次包含结果探针的 batch，不再单独执行标签资格查询和状态回读。
- [ ] A21. 编辑活动的 D1 binding 调用数不随标签数量增长：最多一次旧状态/地区快照读取和一次原子写 batch；未变化的 `event_tags` 关系不会被删除后重写，审计与事实写入同批提交。
- [ ] A22. 标签归并最多使用一次校验/影响范围读取和一次包含关系变更、别名更新与审计的原子 batch，并直接返回可用于详情缓存失效的受影响活动 ID。
- [ ] A23. 单条管理员创建保持事件、标签关系和审计同批原子提交，并将逐标签 statements 收口为集合式 statements；批量创建的现有集合式标签和原子 batch 行为不得退化。
- [ ] A24. 调用计数测试与 D1 `meta.rows_read` / `meta.rows_written` 验证分开报告，证明批处理减少往返而索引、缓存和差异写入才负责减少免费额度消耗。
- [ ] A25. 真实部署 hostname 上的 Cache API 探针记录了 `put` 后 `match` 命中的证据；本地 Miniflare 结果不作为该结论的依据。
- [ ] A26. 报告给出实施前后按路由的 CPU time p50/p99，证明公开读取路径仍在 10 ms 预算内，且 `exceededCpu` 调用数没有上升。
- [ ] A27. 测试证明单次公开读取的缓存+D1 调用数不超过 10，单次写后失效的 `delete()` 不超过 24，且都不随标签数、活动数或地区层级增长。
- [ ] A28. 失效测试证明修改 `110101` 的活动会同时失效 `11`、`1101`、`110101` 三级地区的首页发现键与三个热门窗口键，旧/新地区双侧均覆盖。
- [ ] A29. 自动控制器按 `popularity -> homepage -> detail -> list` 单 scope 推进，并在指标缺失或远程 D1 schema 不兼容时保持当前稳定版本不变。
- [ ] A30. 自动控制器的候选证据包含版本 ID、scope 集合、观察窗口、请求/错误、CPU p50/p99、`exceededCpu`、HTTP 探针、响应哈希、D1 投影比较和最终决定。
- [ ] A31. 失败演练证明候选可以恢复上一稳定版本 100% 流量，旧 Cache API 对象不会在 scope 关闭后被读取，D1 无需恢复。
- [ ] A32. 首页 SSR、首页 API、热门 API、详情和列表路由均复用受测缓存 loader，且保留各自原有错误隔离、404、热度查询、访问 POST、筛选和分页合同。
- [ ] A33. 公开 Worker 不包含 Cloudflare Workers Scripts 写令牌；自动发布权限只存在于外部控制面，且同一时间最多运行一个晋级任务。

## Out of Scope

- 将 D1 替换为其他主数据库。
- 改变活动推荐、热度排名或独立访客的产品口径。
- 为缓存引入付费第三方服务。
- 使用 KV 作为逐访客标记存储、使用浏览器 `localStorage` 作为权威去重依据，或用每日累计计数替代访客最近访问日期。
- 第一阶段引入 Durable Object、Queues 或近似基数算法聚合热度。
- 为数据库层引入 ORM、通用 Repository/Unit of Work、跨请求内存状态或第二套可写标签/活动副本。
- 将首页发现与热门、活动列表与热门标签等不同缓存对象强行合并成一个难以独立缓存和降级的巨型查询。
- 在规划获批前修改产品代码或部署配置。

## Resolved Decisions

- 用户选择允许短暂最终一致：管理员修改已发布活动后，正常服务期间公开数据最多陈旧 60 秒，不要求跨数据中心立即全局可见。
- 第一阶段不使用 KV 作为通用缓存，也不为整个 Astro Worker 开启 Workers Cache；优先采用 Cache API 保存公开 DTO。
- D1 故障降级不属于正常陈旧窗口，允许在明确上限内显示最近安全缓存，并向响应/页面暴露“数据暂时无法刷新”的状态。
- 热度继续使用 `event_visitors(event_id, visitor_key, last_seen_date)` 保存每个活动/IP 的最近访问日期，以精确支持重叠的 3/7/30 日独立访客窗口。
- 热度写入使用独立的 Cache API 当日成功标记抑制重复 D1 调用；Cache API 仅是可丢失优化，D1 约束仍是最终正确性边界。
- 访客清理移出页面访问链路，改为中国本地日期切换后的每日 Cron；热门查询本身始终带窗口条件，因此维护延迟不会展示过期访客。
- 数据库接口采用按职责拆分和业务操作函数的针对性重构；不引入 ORM。公开查询使用 DTO 投影，管理员写入直接返回缓存影响信息，标签关系采用集合式差异更新。
- 用户确认服务会绑定自定义域名 `acg.hobr.site`，因此 Cache API 路径成立；但域名绑定与真实 hostname 上的探针验证是缓存层的前置条件，不是可选项。
- 实施拆为两个子任务：子任务 A（索引改写、Cron 清理、`getDB()` 收口、公开 DTO 投影、管理写入收口、热度当日去重）不依赖 Cache API，先上线并实测；子任务 B（公开 DTO 缓存层）在探针通过、且 A 的生产数据证明仍有需要之后再启动。
- 依据当前 SQL，`event_visitors` 的全表扫描（首页热门两条 CTE + 每次统计 POST 的清理）是免费额度上最先撞线的消耗，其收益量级高于缓存命中率，因此排在缓存层之前。
- 用户要求 pilot 稳定后自动扩大到其他公开 DTO scope。采用外部控制面逐 scope 晋级，不让 Worker 自修改 Wrangler vars；顺序为 `popularity -> homepage -> detail -> list`，缺失指标或失败时停止并回滚。该授权不包含访问去重，也不豁免远程 D1 schema、CPU、响应一致性和错误门禁。
