# 会员购活动导入

## Goal

在管理员新增活动时，允许输入 bilibili 会员购活动 ID，自动读取并预填平台可用的活动信息。管理员能够在发布前检查、修改并补齐无法可靠导入的字段，从而减少重复录入，同时保持现有活动数据质量要求。

## Background

- 用户提供的样例 HAR 对应会员购活动 ID `1004224`，业务数据来自 `GET https://show.bilibili.com/api/ticket/project/getV2`。
- 当前环境已验证该接口可在不携带 HAR Cookie 或登录态的情况下返回活动 JSON。
- 现有管理员新增页会在保存后立即发布活动，见 `src/pages/admin/events/new.astro:22` 和 `src/pages/api/admin/events/index.ts:28`。
- 当前管理员活动验证要求活动名称、类型、规模、区县级行政区、场馆、开始日期、结束日期、来源链接、投稿联系方式，并在创建 API 中要求至少一个规范标签，见 `src/lib/admin/form.ts:239` 和 `src/pages/api/admin/events/index.ts:17`。
- 现有活动表单已经覆盖需要预填和人工编辑的字段，见 `src/components/admin/AdminEventForm.astro:61`。
- 数据库当前没有针对会员购 ID 或 `source_url` 的唯一约束；CSV 批量导入仅通过名称、开始日期和场馆提示疑似重复。

## Requirements

### R1. Import Entry

- 管理员能够在新增活动流程中输入一个会员购活动 ID 并发起导入。
- 输入只接受正整数 ID，不接受任意外部 URL。
- 导入能力仅对已通过现有后台鉴权的管理员开放。

### R2. Reliable Field Prefill

- 系统应从会员购响应中预填能够可靠映射的字段：
  - 活动名称
  - 区县级行政区
  - 场馆和详细地址
  - 开始、结束日期和时间
  - HTTPS 封面 URL
  - 来源链接和购票链接
  - 主办方
  - 入场方式
  - 票价区间
  - 开始购票日期和时间
- Unix 时间戳必须按 `Asia/Shanghai` 转换，不依赖 Worker 默认时区。
- 会员购以分为单位的价格必须转换为用户可读的人民币区间。
- `//` 开头的 B 站资源地址必须规范化为 HTTPS URL。

### R3. Manual Completion and Review

- 导入结果必须进入可编辑的现有活动表单，不能在抓取成功后直接写入数据库。
- 无法可靠导入的字段保持为空，并明确提示管理员补充。
- 活动类型允许给出基于名称的建议，但必须标记为需要确认，不能把未公开的会员购数值类型直接当作平台分类。
- 活动规模、规范标签和会员购未提供的联系信息必须由管理员确认或补充。
- 会员购活动说明中的 HTML、图片和不可信文本不得直接作为 HTML 注入页面；第一版允许活动说明留空后人工编辑。
- 除系统生成的会员购来源标识外，预填的活动业务字段必须允许管理员修改；来源标识保持只读，以支持可靠的重复检测和审计。
- 最终提交继续使用现有活动验证规则，缺少必填字段时不得发布。
- 管理员补齐并确认后，活动沿用现有管理员创建语义立即公开，不进入待审核队列。

### R4. Multi-session and Status Handling

- 对包含多个场次的活动，使用最早开始时间和最晚结束时间预填平台的单一时间范围。
- 多场次被压缩时必须显示清晰警告，提醒管理员检查活动说明和时间。
- 只有会员购响应能够明确表达延期或取消时才映射活动异常状态；无法确认时保持正常/空值，不进行猜测。

### R5. Duplicate Protection

- 如果已有活动使用同一会员购 ID 对应的规范来源链接，必须阻止再次创建，并提供已有活动入口。
- 名称、开始日期和场馆与已有活动相似时，应显示疑似重复警告，由管理员确认后继续。
- 重复检查不能依赖用户提交的任意 URL，必须使用系统生成的会员购规范来源链接。

### R6. Failure and Security Behavior

- 上游超时、网络错误、非 JSON 响应、业务错误或字段结构变化时，页面必须显示可理解的错误，并保留手动新增活动的路径。
- 服务端请求只能访问预先固定的 B 站接口和域名，不能成为任意 URL 代理。
- 不向 B 站转发管理员请求中的 Cookie、Authorization 或 Cloudflare Access 凭据。
- 不在日志、浏览器响应或审计记录中保存完整上游响应；审计信息只记录来源类型和会员购活动 ID。
- 用户提供的 `sample.har` 包含浏览器请求信息，不得直接提交到仓库。测试 fixture 必须只保留解析所需字段并完成脱敏。

## Acceptance Criteria

- [ ] AC1: 管理员输入 `1004224` 后，表单预填“上海·芳文社同人ONLY展2.0~街角兔屋”、上海市宝山区、交运智慧湾科创园25号楼、2026-08-16 12:00 至 21:00、78-138 元、2026-07-23 00:00、主办方和规范会员购链接。
- [ ] AC2: 类型显示为需要确认的建议；规模和标签明确要求人工补充，未补齐时现有发布验证阻止提交。
- [ ] AC3: 除只读的会员购来源标识外，导入结果中的活动业务字段在最终提交前都可由管理员修改。
- [ ] AC4: 多场次活动显示压缩时间范围警告，不会静默丢失“存在多个场次”的信息。
- [ ] AC5: 同一会员购 ID 已存在时不能重复创建，并能导航到已有活动。
- [ ] AC6: 疑似重复但来源 ID 不同的活动只显示警告，管理员确认后可以继续。
- [ ] AC7: 无效 ID、上游错误、超时和响应结构变化均不会写入数据库，并提供手动录入入口。
- [ ] AC8: 导入请求不会携带管理员 Cookie 或认证头，也不能请求用户指定的其他域名。
- [ ] AC9: 测试使用最小脱敏 fixture，仓库中不包含原始 HAR、Cookie、带 token 的资源 URL或完整会员购响应。
- [ ] AC10: 现有手动新增、编辑和 CSV 批量导入行为保持不变。

## Key Decisions

- 导入功能属于管理员新增活动流程，管理员完成检查和必填字段补充后立即发布。
- 第一版只支持单个会员购 ID，不建立通用第三方导入框架。
- 会员购响应只在服务端解析，浏览器只接收规范化后的表单值、缺失字段和警告。
- 不增加草稿状态或多场次数据模型；多个会员购场次压缩到平台现有单一时间范围并提示管理员。
- 不新增数据库迁移；使用规范会员购来源标识、写入前重复检查和导入审计元数据保证来源可追踪。
- 原始 HAR 和完整会员购响应不进入仓库、浏览器或日志。

## Out of Scope

- 定时同步会员购活动的后续变化。
- 批量输入多个会员购 ID。
- 导入或展示会员购订单、库存、实名、退款等票务交易数据。
- 在平台中建立多场次或多票种的独立数据模型。
- 将会员购详情 HTML 或活动图片集合完整复制到平台。
- 支持除 bilibili 会员购之外的任意第三方活动来源。
